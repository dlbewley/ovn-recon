OVN Recon · Architecture Review

Node Visualization

A structural review of the physical topology view, the complexity that is holding it back, and a staged plan for reworking it before VTEP and VRF support land.

2026-08-20epic ovn-recon-s3t23 tasks

The three extracted pure modules — nodeVisualizationSelectors.ts, nodeVisualizationModel.ts, nodeVisualizationLayout.ts — are the healthy part of this code. Right idea, tested, no React entanglement.

Everything else lives in one 2067-line function body where the graph model, the layout math, the SVG renderer, the drawer, and the per-kind detail panels are interleaved. It works. But the cost of adding the next node type is far higher than it should be, and the drawer's problems are structural rather than cosmetic.

02Adding one node type costs ten edits

This is the direct answer to the VTEP question. To add a type today you must touch all of the following, and nothing enforces that you did:

#SiteLocation
1An interfaces.filter(...) bucket:857–911
2The columns array:915
3A near-identical position block:1052–1146 (7 copies)
4A sortByGravity call:986–998 (12 copies)
5The maxRows Math.max list:1189
6A col.key === 'x' && …map() JSX branch:1897–2003 (7 copies)
7getIcon switch + a hex literal at the call site:1213, :1902
8The buildNodeViewModel if/else ladder:1386–1520
9NodeKind union + nodeKindRegistry entry:44, :180
10Edge constructionmodel.ts:60

Each omission fails silently and differently. Miss #3 and the node has no coordinates. Miss #6 and it is positioned but invisible. The connector code at :1856 then quietly return nulls its edges — so the whole thing reads as a data problem rather than a missing case.

nodeKindRegistry at :180 was the attempt at an extension point, and it is the right instinct — it just covers steps 9 and part of 8. Widen it into one descriptor that owns all ten concerns:

interface NodeTypeDescriptor<T> {
  kind:    NodeKind;
  lane:    LaneId;                                    // 2, 3, 5
  match?:  (iface: Interface, ctx: GraphContext) => boolean;   // 1
  id:      (item: T) => string;
  icon:    React.ComponentType;                       // 7
  color:   string;                                    // 7
  label:   (item: T) => string;                       // 8
  badge?:  (item: T) => string;                       // 'VRF' | 'VTEP' | 'CUDN'
  status?: (item: T) => 'up' | 'down' | 'unknown';
  edges:   (item: T, ctx: GraphContext) => Edge[];    // 10
  facts:   (item: T, ctx: GraphContext) => Fact[];    // drives the drawer
}

The ctx carries { nns, interfaces, cudns, udns, nads, routeAdvertisements }. That context object is precisely why the registry has to live inside the component today — the render closures capture props. Pass it explicitly and the registry moves to a module and becomes testable.

With that in place, VTEP-on-dummy is one descriptor plus one lane entry. Today it is a day of whack-a-mole.

03type is used where role is meant

Columns key off the raw nmstate type string, but the property that matters is the interface's role in the topology. Where the two diverge, ad hoc heuristics fill the gap. isBridge at :880:

  • An ovs-interface is a bridge if it is a controller and has no patch…
  • …unless an explicit bridge shadows its name (:887), in which case it is not…
  • …but logicalInterfaces (:894–909) re-includes that same interface anyway via a second rule.

That knot exists purely because there is no role concept to express it in.

otherInterfaces at :911 is a catch-all negation: not ethernet/bond/vlan/mac-vlan/vrf, not a bridge, not an ovs-interface. Anything unrecognized lands in a grey four-wide grid pinned to the bottom of the canvas with no edges drawn at all.

Why this matters for VTEPs

A dummy interface carrying a VTEP will land in that catch-all today — invisible as a topology participant. The temptation will be to add a third heuristic in isBridge's style. Don't. Extract classify(iface, ctx) → role as a pure, ordered rule table first, with each rule named and commented with the nmstate reality it encodes. It is the single highest-value place for tests in the whole epic.

The same applies to VRFs. Today a VRF is a column-6 tenant sharing space with bridge mappings via a hand-stacked currentY and a synthetic header positioned by locating the first VRF node (:1968). If VRFs are to be well represented, they likely want to be a grouping — a container others sit inside — not a column entry. That is a layout-model change, not a rendering tweak.

04Two sources of truth for Y position — resolved

Closed 2026-08-21 · s3t.3

All six render branches now read pos.y; the renderIndex parameter is gone. There is one source of truth, so nodes and their connectors agree by construction rather than by coincidence.

Node Y was computed into the nodePositions map that renderConnector reads, and again from the render index inside the eth, bond, vlan, bridge, logical and networks branches. The l3 and attachment columns already used the map. Where the two disagreed, a node was drawn in one place and its edges terminated in another — and they agreed only while the preceding .filter(nodePositions[...]) dropped nothing.

The comment at the old :1929 — “Recalculate Y position based on render index to eliminate gaps” — marked where this was worked around instead of fixed. It went with the code it described.

The test asserts the invariant, not the arithmetic

NodeVisualization.layout.test.tsx renders the component and checks that every connector endpoint lands on the connection point of a node that was actually rendered. That survives future layout changes in a way that asserting specific coordinates would not. It covers the default view, the view after revealing a hidden column (which shifts every lane rightward), and a fixture that draws no edges at all.

Found on the way

Those tests surfaced a broken fixture: basic-host.json declared the same bridge mapping twice, byte for byte. OVN does not emit a duplicate mapping for one localnet/bridge pair, so the fixture was simply wrong — it rendered two nodes at identical coordinates and tripped React's duplicate-key warning. Deduplicated.

The residual point is real though: resolveNodeId is neither total nor checked for collisions, so bad input degrades into an unsupported React state rather than a visible error. Recorded on s3t.6.

05The gravity layout — resolved

Closed 2026-08-21 · s3t.2, s3t.11

computeGravityById is deleted. Ordering is now layered barycenter within fixed lanes. On a representative two-NIC bonded topology with VLANs, VRFs, CUDNs, UDNs and NADs, edge crossings dropped from 8 to 1.

What was there: ~150 lines scoring nodes as 1000 - (pathLength * 100) - position - (important ? 500 : 0), then tiered subtraction of 5000 / 500 / 50 by band, with br-ex hardcoded as the important node and every id starting with udn- given +50000. Nobody could predict what a new node type would do to ordering.

Three latent defects were confirmed and fixed on the way out:

  • Falsy-zero, three sites. pathGravity reaches exactly 0 on a five-node path through an important node. The fill pass (!gravityById[id]), the important-path chain, and sortByGravity's || 10000 each read that 0 as “absent” — the last of which sorted the highest-priority node to the bottom of its column.
  • Exponential path search. Measured on cliques: 22ms at n=8, 169ms at n=9, 1.7s at n=10, 20.8s at n=11 — roughly 11× per added node. A bridge with a wide fan-out could hang the render.
  • Dead code. sortedCudns and anchorElement, both confirmed by lint.

What replaced it

Lane membership was never the hard part — it is decided by node type. The only open question is order within a lane, which is the standard layered-graph problem. The barycenter heuristic places each node at the average position of its neighbours in adjacent lanes, sweeping left-to-right then right-to-left and keeping the best result by measured crossing count.

Two properties matter as much as the crossing reduction:

  • Deterministic and arrival-order independent. Watched resources arrive in arbitrary order; the seed is group rank then id, so the graph does not rearrange itself between renders. Both are asserted.
  • No hardcoded identities. br-ex centres naturally because nearly everything connects to it. Product ordering preferences — bridge mappings above VRFs, CUDNs above UDNs — now travel as a groupRankById map supplied by the caller, so the layout module no longer knows what a UDN is.

countCrossings is exported alongside it, so a future change has to prove it improves the layout rather than merely altering it.

06Node identity

resolveNodeId (:866) returns a bare iface.name for most interfaces, so interface names share one ID namespace with everything else, and edges are matched by name string. Two workarounds exist because of it:

  • The ovs-interface-shadowing-a-bridge special case at :874, returning interface-<name> for one specific collision.
  • The connector renderer at :1856–1864, which probes both X and interface-X before giving up and silently dropping the edge.

And getFlowPath (:1159) inserts both a-b and b-a edge keys “for safety” because edge identity is not canonical.

One exported nodeId(kind, key) producing iface:br-ex, vrf:blue, cudn:foo, vtep:vxlan0 makes all three disappear — and is a precondition for deep-linkable selection.

07The drawer

Four separable problems sit behind the sense that this panel is troublesome.

It shows stale data

activeNode (:1336) stores a snapshot view model whose .raw is captured at click time. useK8sWatchResource keeps streaming updates, but the drawer never re-derives — the panel shows whatever the cluster looked like when you clicked. Store selectedNodeId and derive with useMemo from current props.

It is expensive

buildNodeViewModel runs inside renderInterfaceNode (:1675) for every node on every render. For VRFs it calls getVrfRoutesForInterface, which walks and dedupes the entire NNS route table — per VRF, per render. All of that work exists solely to feed the drawer.

Per-kind panels are bespoke JSX against any

~500 lines of hand-written DescriptionList (:180–775) reaching into node.raw?.spec?.network?.localNet ?? …localnet. None testable. Summary is a near-strict subset of Details for most kinds, so the tab split earns nothing — and the tabs?: DrawerTabId[] knob at :80 is never populated by any entry. Dead configuration.

Links are built four different ways

getResourceLinks (:93), plus inline template strings at :405, :470, :486, :736, :754, plus a fifth reconstruction in an IIFE in the YAML tab. Some get window.location.origin and target="_blank", some stay relative. Raw <a href> into a console route causes a full page reload, and identical-looking links behave differently depending on which path built them.

Concrete bug — your PatternFly tokens are dead

Sixteen uses of --pf-global--* remain in src/. Those are PatternFly v4/v5 names; the project is on v6, which ships none of them — grep -c -- "--pf-global--Color--200" against react-core's base.css returns 0, versus 2846 hits for --pf-t--global--*. Every one silently resolves to nothing.

Most visibly: attachment nodes pass var(--pf-global--palette--gold-400) as the rect fill (:2011). An unresolved var() in a paint value is invalid — so attachment nodes render black, not gold. Three call sites already use the correct v6 form, so this is unfinished migration, not a design choice.

What would make it genuinely useful

A uniform Fact model instead of bespoke JSX. Per-kind code becomes a pure ~15-line function; one shared renderer handles presentation.

type Provenance = 'observed' | 'declared' | 'inferred';

type Fact = {
  label:      string;
  value:      string | string[];
  ref?:       ResourceRef;   // renders as an SDK ResourceLink
  provenance: Provenance;
  hint?:      string;        // why we believe this
};

Provenance is the point. This is a recon tool, and a large share of what it displays is inferred — yet all of it is presented with identical confidence:

Displayed as factActuallySource
VRF ↔ RouteAdvertisement matchA 15-character name-truncation guess (undocumented IFNAMSIZ heuristic)selectors.ts:97
CUDN associated namespacesRegex-scraped out of a status condition message stringselectors.ts:290
NAD upstream bridgeRegex-extracted from raw config when JSON parse failsselectors.ts:394

An operator debugging a mismatch needs to know which claims to distrust. An inferred chip with a tooltip naming the rule turns a liability into a feature.

Retitle the tabs Overview / Relationships / Config. Relationships is the new value: list the selected node's neighbors as clickable entries that move the selection and re-highlight the path. The data already exists and is simply not exposed — adjacency is built at :778 and getFlowPath (:1146) already walks both directions. That turns the drawer from a leaf view into a navigation instrument.

Answer the question the operator actually has. For a physical NIC the useful fact is not its MTU — it is which CUDNs and UDNs ultimately ride on this wire. That is getFlowPath filtered to network-kind nodes: two lines of derivation on machinery you already have, and the reason someone opened the panel.

Surface diagnostics. You already compute most of the detection implicitly and discard it — a bridge mapping no CUDN references (:275), a VRF port matching no interface, a NAD whose config failed to parse. Surfaced as per-node findings with a badge on the canvas, the tool crosses from diagram to diagnostic.

09The spike runs first

Decision, 2026-08-20: this runs ahead of the rest of the epic. It is half a day, and it gates the two largest downstream investments — the layout replacement and VRF containers — plus keyboard accessibility, since react-topology owns node interaction if adopted.

@patternfly/react-topology is what the OpenShift console's own topology view uses. It would provide pan/zoom, selection, side panels, edge routing, node badges, status decorators and grouping out of the box — several hundred lines of hand-rolled code here does that today.

Two questions, and only two

Q1 — primary, kill criterion

Can a custom layout reproduce the fixed vertical lanes exactly? The left-to-right arrangement encodes the physical-to-logical progression an operator reads, and it is a confirmed value proposition of the app — not an implementation accident. It is not negotiable in a migration. The library accepts custom layouts, so this should be achievable, but verify it against the real lane count (up to ten today) rather than a toy example. If lanes cannot be reproduced cleanly, reject and stop — nothing else matters.

Q2 — the reason to adopt

What does grouping look like for VRF, and would it extend to EVPN/VTEP constructs? The hard part is that VRF members live in other lanes, so a container must span lanes. Confirm lane-spanning containers actually work — a grouping feature that cannot cross lanes does not solve the VRF problem.

Explicitly deferred

Shared-module version skew against the console's provided modules. A real hazard for a dynamic plugin, but solving skew detection is wasted effort if the spike fails on Q1 or Q2. Assume it is workable for the spike's duration. If the spike passes, this becomes a gating question before adoption is committed — file it as a follow-up bead then, and do not let it slip.

Migration cost. Hard to answer honestly against the current 2067-line component, and much cheaper after the model extraction (s3t.5) and descriptor registry (s3t.9) land. Revisit then, when it is a smaller question.

What the spike does not protect

Worth being clear about scope: react-topology consumes a model you hand it, so it does not own most of what this epic rebuilds. Fixtures (s3t.23), extraction (s3t.5), canonical IDs (s3t.6), the lane table (s3t.7), classify() (s3t.8), the descriptor registry (s3t.9) and the entire drawer rework (s3t.12–s3t.16) are required either way. Only s3t.11, s3t.21 and s3t.17 are genuinely gated.

The Phase 0 bug fixes are worth doing regardless. s3t.3 deletes six lines to fix a visible bug that ships this week, against a migration that ships in weeks — fixing something you may later delete is shipping, not waste.

A rejection is a successful spike. Record the outcome on the bead either way, with reasons, so the option is not revisited without new information.
